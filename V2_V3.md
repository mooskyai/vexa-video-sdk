# Vexa Video SDK — Version 2 and Version 3 Roadmap

Repository:

```text
https://github.com/mooskyai/vexa-video-sdk
```

Primary branch:

```text
main
```

Reference implementation studied for Version 2:

```text
https://github.com/remotion-dev/remotion
```

## Important implementation rule

Version 2 is inspired by the functionality and developer experience available in Remotion, but Vexa must implement these capabilities independently.

Do not copy or port Remotion implementation code into Vexa.

Vexa should build equivalent functionality using its existing architecture:

```text
Vexa composition API
        ↓
Serializable composition/project model
        ↓
Deterministic planning
        ↓
Browser preview or Node render runtime
        ↓
Vexa timeline / media / FFmpeg engine
```

The objective is functional capability parity where it makes sense, not API or source-code cloning.

# Version 2 — Programmable Video Creation

## Objective

Version 2 adds a programmable video creation system on top of the existing Vexa media engine.

Vexa 1.x already provides:

- media probing;
- video editing;
- audio processing;
- timeline composition;
- captions;
- transitions;
- hardware acceleration;
- HLS/DASH;
- storage;
- distributed jobs;
- Angular integration;
- plugins;
- AI adapters;
- CLI;
- editor state;
- hosted-render contracts.

Version 2 should add the missing layer that allows developers to define dynamic videos using code and render the same composition through:

```text
Code
 ↓
Composition
 ↓
Interactive Preview
 ↓
Browser Player
 ↓
Local Render
 ↓
Server Render
 ↓
Cloud Render
```

The key principle is:

```text
Composition definition is the source of truth.
```

The same composition should power preview, rendering, automation, templates, and applications.

# V2.1 — Composition Runtime Foundation

## Objective

Introduce the central programmable composition abstraction.

A composition represents a deterministic video or image program.

Example:

```ts
const composition = defineComposition({
  id: "product-demo",

  width: 1920,
  height: 1080,
  fps: 30,
  durationInFrames: 300,

  render(ctx) {
    // composition definition
  }
});
```

## Composition metadata

Every composition should expose:

```ts
interface CompositionDefinition {
  id: string;
  width: number;
  height: number;
  fps: number;
  durationInFrames: number;
}
```

Support:

- dynamic duration;
- dynamic dimensions;
- default props;
- input props;
- metadata calculation;
- validation;
- schema versions.

## Composition registry

Applications should be able to register multiple compositions.

```ts
registerComposition(ProductVideo);
registerComposition(SocialShort);
registerComposition(Thumbnail);
```

And discover them:

```ts
const compositions = await listCompositions();
```

## Still compositions

Support image-only compositions.

```ts
defineStill({
  id: "youtube-thumbnail",
  width: 1280,
  height: 720
});
```

## Serializable composition graph

The runtime should compile programmable composition definitions into Vexa's deterministic project model where possible.

```text
Composition
    ↓
Composition Graph
    ↓
VideoProjectAst
    ↓
Execution Plan
```

## Acceptance

- deterministic frame evaluation;
- serializable composition metadata;
- input schema validation;
- multiple compositions;
- still compositions;
- automated tests;
- Windows acceptance;
- README update.

# V2.2 — Frame Runtime and Animation API

## Objective

Provide frame-based deterministic animation.

## Current frame

Equivalent concept:

```ts
const frame = useFrame();
```

or framework-neutral:

```ts
context.frame
```

## Composition configuration

Expose:

```ts
const {
  fps,
  width,
  height,
  durationInFrames
} = useComposition();
```

## Interpolation

Example:

```ts
const opacity = interpolate(
  frame,
  [0, 30],
  [0, 1]
);
```

Support:

- clamp;
- extend;
- easing;
- multiple ranges;
- color interpolation.

## Spring animation

Example:

```ts
const scale = spring({
  frame,
  fps,
  config: {
    damping: 12,
    stiffness: 100
  }
});
```

## Easing

Provide common easing functions:

```text
linear
ease
ease-in
ease-out
ease-in-out
cubic bezier
```

## Deterministic random

Provide seeded randomness.

```ts
const value = random("particle-42");
```

The same frame must always generate the same value.

## Freeze

Allow freezing part of a composition at a particular frame.

## Loop

Support repeating compositions or sections.

## Sequences

```ts
sequence({
  from: 30,
  durationInFrames: 60
});
```

## Series

Support sequential sections without manually calculating offsets.

## Acceptance

- deterministic output;
- interpolation tests;
- spring tests;
- nested sequence tests;
- frame offset tests;
- browser/Node consistency.

# Architecture Commitments Across V2 and V3

## Backend-neutral core

`@vexa-video/core` must remain backend-neutral and serializable where practical.

## Node execution boundary

`@vexa-video/sdk` remains the primary Node execution package.

## Browser isolation

Browser packages must not runtime-import:

```text
@vexa-video/sdk
node:*
child_process
FFmpeg execution code
Redis clients
filesystem APIs
```

## React isolation

React should be an authoring adapter.

Do not make React a dependency of the deterministic media engine.

```text
@vexa-video/react
       ↓
composition runtime
       ↓
core
```

## FFmpeg safety

Processes must use argument arrays rather than shell-concatenated command strings.

## Deterministic rendering

The same:

```text
composition
+
frame
+
input props
+
assets
```

should generate the same render result where platform media behavior allows it.

## Inspectable planning

```text
Composition
    ↓
Composition Graph
    ↓
VideoProjectAst
    ↓
Execution Plan
    ↓
Render
```

Expensive rendering should remain inspectable before execution.

## Cross-platform behavior

Explicitly test:

```text
Windows
Linux
macOS
```

for:

- paths;
- subprocesses;
- fonts;
- codecs;
- manifests;
- hardware;
- temporary files.

## Documentation

Every implementation stage must update public documentation where relevant.

Public `README.md` must remain professional and must not use the word `Milestone`.

Development tracking may remain in:

```text
ROADMAP.md
docs/MILESTONE-TESTING.md
```

## Quality gate

Every completed feature should include:

- typed contracts;
- runtime validation;
- deterministic planning where applicable;
- unit tests;
- integration tests;
- browser tests when applicable;
- FFmpeg tests when applicable;
- Windows-specific acceptance where applicable;
- documentation;
- examples;
- no regression in `npm run verify`.
